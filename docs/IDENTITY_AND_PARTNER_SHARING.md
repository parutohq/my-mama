# MAMA identity and pregnancy support links

The public homepage is a MAMA World preview. It lets a visitor choose a journey and check an `@username` before registration. The check is informational; it does not reserve the name. The browser keeps only the chosen journey, display name and candidate username in session storage while moving to registration. No health records are stored there.

Registration asks for an email, password, username and explicit confirmation that the person is at least 13. The server validates the confirmation, and an Auth insert trigger persists its version and timestamp with the new account. After email verification, the signed-in first-run screen claims the username through `claim_mama_identity`. The database unique index resolves concurrent claims atomically. Existing accounts also pass through this first-run screen before using the updated app. Username and age-attestation fields are not writable by ordinary profile updates. Accounts created outside the MAMA registration route cannot enter the app without the first-run claim and confirmation; the Auth provider itself is not a globally closed registration boundary. The age confirmation is a self-attestation and does not establish an exact date of birth or adult status. A future age-group experience must request an explicit 13–17/18+ choice and should not infer it from this confirmation.

`/@username` is the canonical public profile URL. Profiles are private by default. The public page obtains only `username`, display name, optional bio and avatar reference from a restricted database function. It never joins to journey, pregnancy or care tables. Settings allow the owner to publish or hide the basic profile and edit the bio. Usernames are intentionally immutable for this release. A future change should use a dedicated transactional rename function, recheck reserved names, and decide whether to retain a non-sensitive redirect; it must never expose private history via old handles.

The Pregnancy Journey can create an opt-in support link only when an active pregnancy record exists. The browser selects from week/trimester, approximate progress, estimated due date and next appointment **date only**. Default scope is week and progress. Durations are 24 hours, 7 days or 30 days. The server creates a 256-bit random token, stores only its SHA-256 hash, and displays the URL once. The owner can revoke an active link or rotate it to a new token. The anonymous page hashes the token and calls `resolve_pregnancy_share`, which checks expiry, revocation and active journey before returning only selected fields. It does not return the owner identity, symptoms, medications, notes, check-ins, investigations, conversations or clinician messages. Anonymous roles have no direct table access to link rows. The page sets no-store, no-referrer and noindex response policies.

The in-memory request throttle is an abuse friction layer, not a distributed rate limit. Token entropy and the narrow database projection are the primary confidentiality controls. Avoid including support URLs in analytics, support tickets or logs. The generated URL should only be sent to a person the owner trusts.

## Release gate

The migration is `supabase/migrations/20261006121101_identity_and_pregnancy_sharing.sql`. Run `supabase test db`, including `supabase/tests/identity_and_partner_share.sql`, against an isolated local database before applying it to any hosted environment. Preview and Production use the same Supabase project in this repository, so a Preview web deployment is **not** a database isolation boundary. Recheck RLS grants, claim races, public/private profile behavior, link scope, expiry, revocation, and direct anonymous table access in that controlled environment. Then apply the migration before enabling the new app build; the app routes depend on its columns and functions.
